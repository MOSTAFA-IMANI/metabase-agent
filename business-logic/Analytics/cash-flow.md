# BNPL cash-flow projection

The workbook is a six-month scenario model. The current version uses September 2026 as its last actual month and forecasts October 2026 through March 2027. Its source cutoff is 2026-10-01 00:00 Asia/Tehran. See [BNPL schema](../BNPL/schema.md) for the transaction path.

## What the model answers

The workbook estimates monthly customer collections, financing inflows, merchant cash-out, net cash flow, ending cash, and any funding gap. It separates opening receivables from cash generated by forecast-period invoice cohorts.

Workbook sheets:

| Sheet | Role |
|---|---|
| `Summary` | Six-month cash projection and key planning inputs |
| `Assumptions` | Editable NMV plan, product mix, schedule profiles, collection curve, opening AR, cash, and merchant cash-out ratio |
| `Projection Build` | Monthly formulas, opening-AR schedule, and target-cohort collection schedule |
| `Historical Actuals` | Reconciliation of Metabase monthly questions with gateway-confirmed cash timing |
| `Repayment Behavior` | Product/term mix, installment amount profiles, collection curve, and historical cohort timing |
| `Source & Notes` | Question references, method, and limitations |

## Source path and timing

1. Completed invoice rows come from `invoices`, filtered by `status = 'CONFIRMED'` and grouped by `created_at` in Asia/Tehran.
2. Invoice amount is the NMV input. Invoice cash/credit components are available in `bnpl_invoice_transactions`; an invoice may have multiple downstream rows, so preserve invoice grain before summing.
3. Installment schedule rows link to gateway payments directly through `payment_id` or through the transaction-item bridge used in the source extractor. Ambiguous bridge mappings are not assigned to invoice cohorts.
4. A row with `confirmed_at` before the cutoff is placed in its confirmation month. The model uses `due_date` for scheduled timing and `confirmed_at` for realized cash timing.
5. Historical Metabase question 290 uses gateway payment creation timing, so it is a comparison series rather than the model's cash-recognition source. Question 280 provides accounts-receivable context; its `payment_id` proxy is not confirmation evidence.

- [Question 280: AR Amount Monthly](https://mt.soupop.ir/question/280)

## Forecast logic

- Target NMV is divided between a four-installment model and a non-four-installment “Loan” model using linked-invoice installment indices. The builder labels an invoice as the four-installment model when its maximum stored installment `number` is 4; this is an analytical proxy, not a confirmed product taxonomy.
- Each product model uses its observed installment amount share of model NMV and median days from invoice creation to `due_date`.
- For future installments with `number > 1`, the model shifts expected due amounts across cash-receipt months using a historical `confirmed_at` collection curve. Index 1 is modeled separately in its due month.
- Opening unpaid receivables are scheduled separately. Receivables overdue before September 2026 are displayed but excluded from projected cash receipts because no age-specific recovery curve was supplied.
- Merchant cash-out is forecast as target NMV multiplied by an observed trailing merchant-settlement ratio.
- An investor cash inflow is entered for October only. It is financing, not customer revenue.
- No verified opening bank balance was available. The workbook exposes 0.0M as an editable starting-cash assumption. It does not add unsupported payroll or other operating costs.

## Installment index warning

Owner clarification on 2026-10-13 supersedes this section's previous index rule: `number = 1` is payable at invoice time and must be excluded from AR/DSO. The existing cash-flow extractor still treats number 1 as a scheduled installment and should be reviewed before using its first/later installment split or forecast as an operational source of truth. The new AR/DSO dashboard follows the updated rule; this note does not silently change the existing forecast code or workbook.

The collection curve is trained on `number > 1`, so it does not estimate invoice-time payment behavior. Under the updated rule, the extractor's treatment of number 1 needs review: the new DSO dashboard reports it separately as invoice-time payment. If number 0 appears, its meaning must be confirmed before including it in any forecast bucket. If invoice-time payments are stored outside `bnpl_credit_installments`, the source model will not see them through this path.

## Limitations and refresh notes

- Amounts in the workbook are displayed in million Toman; database amount fields are numeric values whose unit conventions must be confirmed for any new source.
- The current model treats a confirmed installment as full settlement of `installment.amount`. Partial settlement, refunds, reversals, and duplicate payment attempts need validation.
- Product classification uses maximum installment index. Small non-four terms remain in the “Loan” bucket; six-installment amounts are shown separately.
- The model excludes records that cannot be mapped uniquely to an eligible invoice. This affects linkage coverage.
- An explicit forecast assumption is not observed cash. Read the `Assumptions` sheet before quoting any forecast output.
- To refresh, inspect the source queries and update the `AS_OF` cutoff and forecast periods together. The output path and formulas are in the linked builder scripts; do not treat the inspected `.ndjson` file as a workbook source.
